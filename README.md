# AdSight

An ad campaign performance dashboard over 10,000 campaigns: browse and filter a
large table, drill into a campaign, and ask questions in plain language. The
vocabulary follows the Apple Search Ads Campaign Management API — supply sources,
serving state reasons, tap-through rate, billing events — so the surface is
recognisable if you have used that product.

```
apps/web    Next.js 15 App Router, React 19, React Query + Redux Toolkit
apps/api    Express 5 BFF — aggregates four upstreams, serves REST + GraphQL
packages/types   domain model, filter model, URL codec — shared by both apps
packages/ui      shared components and the cached Intl formatters
```

## Running it

```bash
npm install
npm run seed          # generates the 10,000-campaign fixture (~1.5s, deterministic)
npm run dev           # api on :4000, web on :3000
```

The seed step is required — the API refuses to boot without it rather than
serving an empty dashboard. `apps/api/data/` is gitignored: the generator is
deterministic given `(SEED, SEED_END_DATE)`, so CI regenerates the 18 MB metrics
file in about a second instead of the repo carrying it.

The natural-language query bar works with no configuration, answered by a
built-in keyword parser. To use Claude instead, set `ANTHROPIC_API_KEY` on the
API; `/api/ai/status` reports which planner is live and the UI labels the panel
accordingly.

## Measured performance

Numbers below are from `perf/render.json` and `perf/bundle.json`, regenerated by
`npm run perf` and `npm run measure:bundle`. Median of 5 runs, headless Chromium,
production build, M-series laptop. Method notes are in each JSON file.

### Table rendering, 10,000 rows

The `/perf` route mounts two table implementations over the **same** row array and
times them. `CampaignTableNaive` is the natural first version: every row in the
DOM, no memoization, a `new Intl.NumberFormat(...)` per cell, and one `<circle>`
per sparkline point. `CampaignTable` adds virtualization, `React.memo` on the row,
module-level cached formatters, a fixed row height, and a single `<path>` sparkline.

| | Naive | Virtualized + memoized | |
|---|---:|---:|---|
| Mount to painted frame | 6,472 ms | **34 ms** | 190x |
| Scripted scroll, 30 frames | 2,063 ms | **501 ms** | 4.1x |
| Median frame | 68.1 ms | **17.5 ms** | 3.9x |
| Worst frame | 95.1 ms | **23.9 ms** | 4.0x |
| Frames over 16.7 ms | 30/30 | **19/30** | |
| DOM elements | 510,025 | **463** | 1,100x |

Two honest caveats. The optimized scroll figure is bounded by the display refresh
rate, not by the work — 30 frames at 16.7 ms is 501 ms, which is exactly what it
reports, so 4.1x is a floor rather than a measurement of headroom. And the naive
mount number varies with machine load by roughly ±15% across runs; the optimized
one does not move, because it renders a constant ~25 rows regardless of dataset
size. That constant-cost property is the actual result. At 1,000 rows the naive
version mounts in 583 ms and the optimized one in 33 ms; at 10,000 the naive
version is 11x slower again while the optimized one is unchanged.

### Initial JavaScript

Recharts is the largest dependency in the app, and the drill-in route is the only
place a chart renders. Measured in the browser, on a cold load per route:

| Route | JS transferred | Contains Recharts |
|---|---:|---|
| `/` (campaign list) | 518 KB | no |
| `/campaigns/[id]` (drill-in) | 903 KB | yes, 376 KB |

**The interesting part is that this started out wrong.** The first version routed
all three deferred panels through a single `lazy.tsx` barrel. `next/dynamic`
correctly deferred *executing* Recharts, but because the campaign list imported
that barrel for the AI panel, and the barrel also referenced the chart, the chart
chunk was registered against the list route too. Splitting the barrel into one
module per component took `/` from **253 KB to 151 KB gzip** — a 40% reduction on
the route users land on, for a change that is purely file organisation.

I would not have found it by reading the code; `next/dynamic` was in the right
place and the intent was correct. It showed up because the before/after
measurement came out at +0.1%, which was implausible enough to go looking. The
write-up is in [`apps/web/src/components/lazy/README.md`](apps/web/src/components/lazy/README.md).

The corollary is the part worth stating plainly: **applying `next/dynamic` to my
own small components measured as no change at all** (150.8 KB vs 150.9 KB gzip).
The panels are a few KB each; deferring them is tidy but it is not a performance
result, and the repo does not claim it as one. The measurable win was entirely in
keeping one heavy third-party dependency off a route that never uses it.

## Why the state is split this way

**Redux Toolkit holds the question; React Query holds the answer.**

Filters, sort, date range, column visibility and row density go in Redux. They are
client state: nothing on the server owns them, they are edited from many
disconnected places — the toolbar, the filter panel, a column header, the AI plan
review, the URL on first load — and several of them have to be read *together* to
build one request. Component state would mean prop-drilling through the table;
putting them in React Query would mean storing user intent in a cache that is
allowed to evict it.

Campaign lists, campaign details and filter facets go in React Query. They are
server state, and the problems they bring are caching, deduplication, background
refetch, pagination and request cancellation — all of which React Query solves and
none of which a reducer does. Putting them in Redux would mean hand-writing
loading flags, staleness rules and an invalidation strategy.

The seam is one selector,
[`selectQueryString`](apps/web/src/store/selectors.ts): it encodes the Redux
filter into the string that is simultaneously the React Query cache key, the
request URL, and the browser URL. Three consequences fall out of that:

- Changing a filter creates a new cache entry rather than triggering an
  imperative refetch, so returning to a previous filter is instant.
- Opening the filter panel or changing row density produces the *same* string, so
  React Query does not refetch. There is a test that asserts exactly this.
- A filtered view is a shareable link, and the URL the browser writes is parsed by
  the server with [the same codec](packages/types/src/querystring.ts) — so the
  address bar, the cache, and the server cannot disagree.

## The BFF

`apps/api` fans out to four simulated upstreams with independent latency and
failure behaviour: campaign config, reporting, app catalog, and budget pacing. The
ordering in
[`campaignAggregator.ts`](apps/api/src/orchestration/campaignAggregator.ts) is the
part that matters:

1. campaign config — cheap, cacheable
2. filter on config — 10,000 rows down to typically a few hundred
3. reporting — roll up **only** the survivors, over the resolved date range
4. filter on metrics, sort, then slice to one page
5. catalog + pacing — for the page only, both in flight at once

Steps 1–4 are why a metric threshold across 10,000 campaigns is affordable; step 5
is why a 50-row page costs two batched upstream calls instead of a hundred. A
filtered query returns in ~5 ms and an unfiltered one in ~30 ms.

The budget service fails 6% of the time by default. The aggregator catches that
specific error, returns `pacing: null` per row, and names the failure in
`meta.degraded` so the UI shows a banner instead of an error page. Anything that
is *not* an `UpstreamUnavailableError` is rethrown as a 500 — a real bug should not
be silently downgraded to a missing column, and there is a test for that
distinction.

### REST and GraphQL over the same aggregator

Both surfaces call the same orchestration. The difference is field-level laziness:
`app` and `pacing` are resolved as thunks, so a GraphQL query that selects only
name and spend never touches the catalog or budget upstreams, while the equivalent
REST call always does — its response shape is fixed. Per-request batch loaders
collapse a 25-row page into one catalog call rather than 25.

Both claims are asserted with spies in
[`graphql.test.ts`](apps/api/src/graphql/graphql.test.ts), because the response
body looks identical either way.

## The natural-language query bar

The model never mutates the view. It calls one strict tool that *proposes* a
filter; the rationale streams token-by-token over SSE while the structured
proposal arrives as a separate typed event; the UI renders it as plain-language
chips and applies nothing until the user presses Apply.

Three details make the review real rather than decorative. The chips are derived
from the same filter object that will be applied, so the preview cannot drift from
the effect. `unsupported` is shown as prominently as the chips — a planner that
quietly drops half a request is worse than one that says it could not do it. And
accepting dispatches the same `viewReplaced` action that URL hydration uses, so an
AI-applied filter is indistinguishable from a hand-built one, including in the URL.

Without an API key, a deterministic keyword parser answers instead, producing the
same `FilterPlan` type through the same validation — so the feature demos and its
tests run with no network and no credentials. It is also the part of the feature
that can be tested exactly, and
[its test file](apps/api/src/ai/heuristic.test.ts) is mostly regressions:
`worst CPA` has to sort *descending* because for a cost metric higher is worse,
and `ttr below 2%` used to bind to the `7` in "last 7 days" because the matcher
looked for the nearest number in either direction instead of the one following the
comparator.

Model calls use `claude-opus-5` at `effort: "low"` with thinking left on.
Disabling thinking on Opus 5 can make it emit a tool call as plain prose, which
would silently break the planner — the turn succeeds and no filter is ever
produced. Server-side refusal fallback is requested and degrades gracefully if the
beta is unavailable on the account.

## Tests

121 unit tests and 10 end-to-end tests, all run in CI on every PR.

```bash
npm test              # vitest across all workspaces
npm run e2e           # playwright, builds and starts both servers itself
```

| Where | What |
|---|---|
| `apps/api` (71) | date-range resolution, two-pass filtering, unit conversion, derived-rate divide-by-zero, upstream degradation, REST integration against the real fixture, GraphQL laziness and batching, the heuristic planner |
| `apps/web` (32) | reducer behaviour, the query-string seam, URL codec round-trip, virtualization row counts, table accessibility, the AI review gate |
| `packages/ui` (18) | formatter caching, sparkline path generation and its degenerate cases |
| `e2e` (10) | filter → shareable URL → drill in → create campaign, plus propose-and-apply and propose-and-discard |

The E2E suite runs against a production build. `NEXT_PUBLIC_API_URL` is inlined at
build time, so the Playwright config builds inside its `webServer` command rather
than assuming a prior build pointed at the right API.

Two bugs found by writing these tests, both fixed:

- **An unbounded render loop on page load.** `CreateCampaignDialog` had the object
  returned by `useMutation` in an effect's dependency array and called
  `mutation.reset()` inside it. That object is a new identity every render, so the
  effect re-ran, reset notified its observers, and the cycle never terminated.
  Because the dialog stays mounted while closed, it fired immediately — and it
  starved the URL-sync effect, so no filter ever reached the address bar.
  Depending on `mutation.reset`, which is stable, fixes it.
- **`aria-sort` on the wrong element.** It was on the header's `<button>`, whose
  implicit role does not support it, so the sort state was never announced. The
  table is now a real ARIA grid with `aria-sort` on the `columnheader` and
  `aria-rowcount` reporting the full result size — otherwise virtualization makes
  a screen reader say "row 12 of 25" on a 10,000-row set.

## Deploying

`apps/web` is a standard Next.js app; `apps/api` is a Node service that needs
`npm run seed` in its build step. See [DEPLOY.md](DEPLOY.md) for both, including
the one environment variable that has to be set at build time rather than runtime.

## Scope

Deliberately not built: authentication, billing, multi-tenancy, or writes beyond
creating a campaign. The upstreams are in-process fixtures behind a swappable
client interface rather than real services. The data is generated, and the
dashboard says so — date presets resolve against the fixture's last day rather
than the wall clock, and the footer shows the window being displayed.
